## 2. Guide-image construction recipes (concrete, step-by-step, covering stroke weight, solid-vs-dashed, fill choices, resolution, aspect-lock tricks)

### Recipe A: gpt-image guide raster for whole-panel composition

1. Export the SVG dieline to a raster whose pixel aspect ratio exactly matches the intended output size, because OpenAI documents `size` as an output option and `gpt-image-2` accepts arbitrary sizes that satisfy max-edge, multiple-of-16, aspect-ratio, and total-pixel constraints. (https://developers.openai.com/api/docs/guides/image-generation)
2. Use a first draft size near the production aspect rather than relying on `auto`, because OpenAI documents concrete `size` choices and `auto` model selection separately. (https://developers.openai.com/api/docs/guides/image-generation)
3. For `gpt-image-2`, keep both output edges multiples of 16 px and keep the long-edge/short-edge ratio at or below 3:1, because those are explicit OpenAI size constraints. (https://developers.openai.com/api/docs/guides/image-generation)
4. Use 1024-class or 1536-class drafts for early iteration when matching older gpt-image/gpt-image-1.5 shapes, because OpenAI's prompting guide lists `1024x1024`, `1024x1536`, and `1536x1024` for `gpt-image-1.5` and `gpt-image-1`. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
5. Use the exact die-cut outer silhouette as a pale gray filled body on a white or transparent background, because image references and edit inputs are documented but OpenAI does not document a separate ControlNet-like control channel for gpt-image. (https://developers.openai.com/api/docs/guides/image-generation)
6. Put the outer contour and internal cutouts on top as solid lines, not dashed lines; dashed-line leakage is an internal task observation and is not web-verified in the sources found, so treat "avoid dashed guide marks" as an internal production rule rather than a public model fact. [unverified/internal observation]
7. Use neutral dark gray or muted blue guide strokes rather than saturated red/green marks when the marks are not meant to appear in the output; this is a risk-reduction heuristic, not an externally verified gpt-image rule, and it is motivated by OpenAI documenting strong text and structured visual rendering rather than non-rendered annotation semantics. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
8. Do not put literal labels like "WINDOW HERE" inside the guide unless you are willing to post-check for text leakage, because OpenAI's prompting guide advertises reliable text rendering and complex structured visuals, while no cited OpenAI page guarantees that drawn text labels are treated as non-output annotations. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
9. If labels are needed for human readability, put them outside the die-cut body in a disposable margin and ask the model to follow the layout marks but omit all guide marks; this is a heuristic, and no official source found guarantees the annotations will be omitted. [unverified/hypothesis]
10. Encode window/door positions as visible simple shapes rather than only prose, because ControlNet, GLIGEN, and BoxDiff all exist to supply non-text spatial conditions when text alone is insufficient. (https://arxiv.org/abs/2302.05543 ; https://arxiv.org/abs/2301.07093 ; https://arxiv.org/abs/2307.10816)
11. Use separate style references for watercolor medium, palette, illustration vocabulary, and feature exemplars, because OpenAI documents style control/style transfer workflows and Google documents up to multiple reference images for Gemini image models. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide ; https://ai.google.dev/gemini-api/docs/image-generation)
12. Keep the guide image visually boring and schematic, because the production intent is for style references to carry watercolor look while the guide carries geometry; this is an inference from the task decomposition and from documented model support for image references and style control. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)

### Recipe B: ControlNet Canny / lineart raster from SVG

1. Rasterize the SVG at the same width and height you plan to sample, because Diffusers documents that the ControlNet input image dimensions default the output dimensions and that images are resized if height/width are passed. (https://huggingface.co/docs/diffusers/en/api/pipelines/controlnet)
2. Start SDXL control rasters around 1024-square-equivalent area, because the Xinsir Canny SDXL card resizes control images to a 1024 x 1024 bucket-equivalent area for best performance. (https://huggingface.co/xinsir/controlnet-canny-sdxl-1.0)
3. Use black lines on white background for Canny/lineart experiments, because Diffusers constructs a Canny control image with OpenCV and feeds that edge image as the ControlNet condition. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
4. Use solid strokes for exact architecture and avoid dashed strokes, because Canny extracts edges and a dashed contour becomes many short edge segments; the extra claim that dashes leak into final art is internal/unverified unless confirmed by your own artifacts. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
5. Start architectural strokes at roughly 3-6 px on a 1024 px short edge and scale proportionally with resolution; this stroke-width value is a practical heuristic, not a published universal threshold. [unverified/hypothesis]
6. Keep tiny decorative strokes out of the control map unless they must be enforced, because Diffusers states the control image is additional guidance and `controlnet_conditioning_scale` controls how much weight is assigned to it. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
7. For FLUX Canny ControlNet, start with `controlnet_conditioning_scale=0.5`, because the Diffusers FLUX Canny example uses `0.5`. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
8. For SDXL Xinsir Canny, start with `controlnet_conditioning_scale=1.0`, because the Xinsir Canny model card example sets the variable to `1.0`. (https://huggingface.co/xinsir/controlnet-canny-sdxl-1.0)
9. For multi-control Canny plus depth, start with `[0.5, 0.5]`, because Diffusers uses that scale pair in its Canny+depth Multi-ControlNet example. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
10. Sweep control scales rather than treating a published example as a law, because Diffusers defines `controlnet_conditioning_scale` as the multiplier applied before ControlNet outputs are added to the UNet residual. (https://huggingface.co/docs/diffusers/en/api/pipelines/controlnet)
11. Mask multiple condition images so Canny, depth, and segmentation do not fight over the same pixels, because Diffusers explicitly recommends masking conditionings so they do not overlap in Multi-ControlNet. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
12. Prefer Canny or lineart for die-cut contour and window/door grid placement, because these controls encode visible edges while depth/normal primarily encode volume and surface orientation. (https://arxiv.org/abs/2302.05543 ; https://huggingface.co/xinsir/controlnet-union-sdxl-1.0)
13. Prefer segmentation for coarse zones such as "building body", "window zone", and "sky/background" rather than for exact mullions, because segmentation is listed as a ControlNet condition type while edge controls are listed separately. (https://arxiv.org/abs/2302.05543 ; https://huggingface.co/xinsir/controlnet-union-sdxl-1.0)
14. Prefer depth/normal only when the toy-building relief, bevel, or 3D volume matters more than exact window outline, because Diffusers' Canny+depth example treats depth as an additional control rather than the line-placement control. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)

### Recipe C: Region masks for placement-enforced inpainting

1. Convert each SVG feature zone into a separate same-size alpha mask, because OpenAI requires the image and mask to be the same format and size and requires the mask to contain an alpha channel. (https://developers.openai.com/api/docs/guides/image-generation)
2. Use one mask for one feature class per edit pass, such as one pass for door leaf, one for window cluster, and one for signage blank, because the method's control comes from isolating the edit area rather than asking the model to place several unrelated features at once. (https://developers.openai.com/api/docs/guides/image-generation)
3. Keep the unmasked base panel fixed between local passes, because image editing APIs operate on an input image plus a mask and prompt rather than regenerating the whole image from scratch. (https://developers.openai.com/api/docs/guides/image-generation)
4. Pad masks by a small local bleed around the desired feature boundary when style blending matters, because generative edits need enough pixels around the target to integrate lighting and watercolor edges; this padding amount is a production heuristic, not a cited model guarantee. [unverified/hypothesis]
5. Verify each masked pass against the SVG after generation, because neither OpenAI's mask documentation nor fal's fill-image schema is an acceptance test for die-cut fit. (https://developers.openai.com/api/docs/guides/image-generation ; https://fal.ai/models/fal-ai/flux-general/api)

### Recipe D: Aspect-locking tricks for models that snap to preset ratios

1. If a model offers fixed aspect ratios, choose the nearest ratio and embed the actual die-cut body inside a guide frame with known padding, because fal FLUX endpoints list discrete aspect-ratio or image-size choices and OpenAI documents explicit image-size controls. (https://fal.ai/models/fal-ai/flux-control-lora-canny/api ; https://developers.openai.com/api/docs/guides/image-generation)
2. For `gpt-image-2`, prefer direct custom dimensions that match the die-cut panel ratio if they satisfy OpenAI's multiple-of-16, max-edge, aspect-ratio, and pixel-count constraints. (https://developers.openai.com/api/docs/guides/image-generation)
3. For Gemini/Nano Banana experiments, set `response_format.aspect_ratio` and `image_size` where the API supports them, because Google documents `aspect_ratio` and `image_size` fields in its image API examples. (https://ai.google.dev/gemini-api/docs/image-generation)
4. Put a thin non-output crop frame outside the target silhouette only when the model needs a rectangular framing hint; this is a heuristic, and no cited model doc guarantees the crop frame will be ignored. [unverified/hypothesis]

### Recipe E: Translating box/region research into the gpt-image stack

1. Use GLIGEN/BoxDiff-style boxes as a planning representation, not as a direct gpt-image API parameter, because GLIGEN and BoxDiff expose box-constrained methods in papers/code while OpenAI's image guide documents prompts, image inputs, masks, and size options rather than bounding-box inputs. (https://arxiv.org/abs/2301.07093 ; https://arxiv.org/abs/2307.10816 ; https://developers.openai.com/api/docs/guides/image-generation)
2. Convert each planned box into either a visible guide shape for whole-panel generation or an alpha mask for local inpainting, because OpenAI documents image editing with masks and mask format/size constraints. (https://developers.openai.com/api/docs/guides/image-generation)
3. Keep box labels in the prompt text instead of drawing them inside the panel, because OpenAI documents strong text rendering and no cited OpenAI page guarantees that visible labels are ignored. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
4. Use DenseDiffusion/regional-prompting/Omost outputs as layout compilers when helpful, because those sources describe dense regional captions, regional attention control, or canvas planning, but treat their output as guide data for gpt-image rather than as the final rendering model. (https://arxiv.org/abs/2308.12964 ; https://arxiv.org/abs/2411.02395 ; https://github.com/lllyasviel/Omost)
5. Do not let region prompts carry independent art-direction language unless the goal is region-specific style, because regional prompting sources target compositional control while OpenAI's gpt-image prompting guide supports central style-control prompts and references. (https://arxiv.org/abs/2411.02395 ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)

## 3. gpt-image-specific findings (annotation-following behavior, failure modes, official doc citations)

1. OpenAI officially documents image generation and image editing for gpt-image models, including generating images from prompts, editing input images, and customizing output size, quality, format, compression, and background. (https://developers.openai.com/api/docs/guides/image-generation)
2. OpenAI officially documents mask requirements for edits: the image and mask must be the same format and size, and the mask must contain an alpha channel. (https://developers.openai.com/api/docs/guides/image-generation)
3. OpenAI's `gpt-image-2` size rules allow custom sizes subject to maximum edge, multiple-of-16 edges, long/short ratio, and pixel-count constraints, which makes exact die-cut aspect locking more plausible than fixed-ratio-only models. (https://developers.openai.com/api/docs/guides/image-generation)
4. OpenAI's prompting guide says `gpt-image-2` is the recommended default for new builds and the strongest model for production workflows in that guide. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
5. OpenAI's prompting guide lists complex structured visuals, diagrams, multi-panel compositions, precise style control, and style transfer among gpt-image capabilities. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
6. The reviewed OpenAI image guide and prompting guide do not provide a formal public guarantee that drawn arrows, boxes, or text labels on an input image will be interpreted as non-rendered annotations instead of visual content; this is an evidence gap, not proof of failure. (https://developers.openai.com/api/docs/guides/image-generation ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
7. Annotation leakage into output should be treated as a production risk, because OpenAI advertises strong text rendering and structured-visual generation while not documenting a separate "annotation channel" that strips labels from the output. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
8. The safest gpt-image geometry signal is therefore a clean guide image that looks like a layout reference rather than a marked-up screenshot, because OpenAI documents image inputs and style/control prompting but not non-rendered markup semantics. (https://developers.openai.com/api/docs/guides/image-generation ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
9. For exact placement, use gpt-image masks after the whole-panel pass rather than relying only on drawn annotations, because OpenAI edit masks are explicitly documented and annotation-following is not explicitly guaranteed in the reviewed OpenAI docs. (https://developers.openai.com/api/docs/guides/image-generation)
10. Google documents Gemini/Nano Banana image editing with text plus image inputs, multi-turn editing, reference images, aspect-ratio/image-size controls, and generated-image SynthID watermarking. (https://ai.google.dev/gemini-api/docs/image-generation)
11. Google states Gemini 2.5 Flash Image supports targeted transformations and precise local edits with natural language, and Google says it has seen developers use visual templates for real estate listing cards, employee badges, and product mockups. (https://developers.googleblog.com/en/introducing-gemini-2-5-flash-image/)
12. Google says Gemini 2.5 Flash Image can read and understand hand-drawn diagrams and follow complex editing instructions in a single step, which is stronger public annotation-like evidence than I found in OpenAI's gpt-image docs. (https://developers.googleblog.com/en/introducing-gemini-2-5-flash-image/)
13. A March 2026 Android Central report says Google was working on a Gemini/Nano Banana Mark Up screen with sketch/text annotation options, but that source describes a reported or leaked feature rather than a stable official API guarantee. (https://www.androidcentral.com/apps-software/ai/nano-banana-creates-but-it-might-also-listen-to-the-edits-you-tell-gemini-to-make)
14. Gemini/Nano Banana evidence is relevant for comparison, but the production path in this task is gpt-image, and OpenAI's official docs should outweigh Gemini behavior when choosing the production control method. (https://developers.openai.com/api/docs/guides/image-generation ; https://ai.google.dev/gemini-api/docs/image-generation)

## 4. Recommendations (concrete, ranked, tied to our stack: gpt-image via codex CLI + gpt-image-2 via fal)

1. Use gpt-image as the default production route: build one SVG-derived guide raster for geometry, attach separate style references for watercolor medium/palette/feature vocabulary, iterate with the task-provided Codex CLI path, and reserve the task-provided gpt-image-2 via fal route for finals; the public evidence is OpenAI's documented image-input/edit/size support and prompting guide for production-quality structured visuals. (https://developers.openai.com/api/docs/guides/image-generation ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
2. Make the guide raster schematic, solid, and low-style: pale gray silhouette fill, solid outer contour, solid internal cutout/window/door guides, no dashed lines, no in-body text labels; the no-dash rule is internal/unverified, while the low-style separation is an inference from documented image-reference and style-control capabilities. (https://developers.openai.com/api/docs/guides/image-generation ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
3. For exact feature placement, enforce with region masks after the whole-panel composition pass: one alpha mask per window/door/signage zone, same format/size as the edited image, and one local edit per zone. (https://developers.openai.com/api/docs/guides/image-generation)
4. Treat drawn arrows, boxes, and "window here" labels as experimental gpt-image inputs, not as a production guarantee, because the reviewed OpenAI docs document image editing and masks but do not document non-rendered annotation semantics. (https://developers.openai.com/api/docs/guides/image-generation ; https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
5. Use a visual layout board instead of text labels when possible: draw the desired window/door shapes in place and put any explanatory labels outside the panel body or in the prompt text, because text labels inside the image may be treated as renderable text and OpenAI advertises strong text rendering. (https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
6. Keep ControlNet as a research/B-candidate path, not the primary production finalizer: it has the strongest public geometry-control evidence, but it is not documented as a gpt-image feature and therefore would add an SDXL/FLUX side stack. (https://arxiv.org/abs/2302.05543 ; https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet ; https://fal.ai/models/fal-ai/flux-general/api)
7. If using ControlNet for a geometry study, test Canny/lineart first for architectural line guides, test segmentation second for zone occupancy, and test depth/normal only for facade relief, because those condition types map directly to edge, region, and volume controls in the cited ControlNet sources. (https://arxiv.org/abs/2302.05543 ; https://huggingface.co/xinsir/controlnet-union-sdxl-1.0)
8. Start ControlNet scale experiments at 0.5 for FLUX Canny, 1.0 for Xinsir SDXL Canny, and `[0.5, 0.5]` for SDXL Canny+depth, because those values appear in the cited Diffusers and Xinsir examples. (https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet ; https://huggingface.co/xinsir/controlnet-canny-sdxl-1.0)
9. Do not rely on GLIGEN/BoxDiff/DenseDiffusion/ELLA as production controls unless you are willing to run research code or open diffusion tooling, because the cited sources are papers/GitHub projects rather than documented gpt-image or fal gpt-image controls. (https://arxiv.org/abs/2301.07093 ; https://arxiv.org/abs/2307.10816 ; https://arxiv.org/abs/2308.12964 ; https://arxiv.org/abs/2403.05135)
10. Borrow the idea of box+label planning from GLIGEN/BoxDiff for prompt and guide construction, but render those boxes into a clean guide raster or masks for gpt-image rather than expecting gpt-image to accept explicit bounding-box parameters. (https://arxiv.org/abs/2301.07093 ; https://arxiv.org/abs/2307.10816 ; https://developers.openai.com/api/docs/guides/image-generation)
11. Use Gemini/Nano Banana only as an exploratory comparator for annotation-following, because Google's public claims around hand-drawn diagrams and visual templates are stronger than OpenAI's public annotation claims, but the task production stack is gpt-image. (https://developers.googleblog.com/en/introducing-gemini-2-5-flash-image/ ; https://developers.openai.com/api/docs/guides/image-generation)
12. Gate every candidate with SVG overlay and cutout checks after generation, because none of the cited model docs substitutes for production acceptance against the actual die-cut template. (https://developers.openai.com/api/docs/guides/image-generation ; https://huggingface.co/docs/diffusers/main/en/using-diffusers/controlnet)
